1. Стратегия сопровождения (ГОСТ 12207)

Тип сопровождения: Адаптивное (Adaptive Maintenance) — адаптация к требованиям безопасности без изменения функциональности; Профилактическое (Perfective Maintenance) — контейнеризация и обновление компонент.

Запрос на модификацию MR-2026-001: переход с HTTP на HTTPS на всех сайтах. Инициатор — руководство Компании 1. Приоритет — высокий (угроза ИБ).

Этапы сопровождения:
  1. М-01 — Анализ запроса на модификацию (неделя 1)
  2. М-02 — Разработка ТЗ на изменение (неделя 1–2)
  3. М-03 — Реализация: middleware HTTPS, заголовки безопасности, API, документация (неделя 2–3)
  4. М-04 — Сборка модифицированного контейнера Dockerfile (неделя 3)
  5. М-05 — Тестирование по ГОСТ Р 56920 / IEEE 829 (неделя 3–4)
  6. М-06 — Передача в среду заказчика (неделя 4)
  7. М-07 — Оповещение затронутых сторон (неделя 4)

2. Изменения в архитектуре, операциях и интерфейсах
2.1. Архитектура

До (v1.x — HTTP): браузер обращался по HTTP к Django на устаревшей ВМ Linux (EOL). Шифрование отсутствовало, заголовков безопасности не было, контейнеризации не было.

После (v2.0.0 — HTTPS): браузер обращается по HTTPS к TLS-прокси (Nginx / Replit Proxy), который передаёт запрос Django-приложению в Docker-контейнере по HTTP внутри платформы с заголовком X-Forwarded-Proto: https. HTTP-запросы перенаправляются на HTTPS автоматически (301).

2.3. Изменения в интерфейсах

Пользовательский веб-интерфейс: ранее доступ по http:// (браузер отмечал «не защищено»), теперь автоматический редирект на https:// с отображением замка.

API контейнера: ранее все эндпоинты были доступны по HTTP, куки sessionid и csrftoken не имели флага Secure. После модификации все API-эндпоинты доступны только по HTTPS, куки помечены Secure и HttpOnly, добавлен заголовок Strict-Transport-Security.

Внутреннее взаимодействие: ранее контейнер и приложение работали на разных ВМ по HTTP. Теперь контейнер вызывает восстановленное приложение по HTTP на localhost (внутри платформы Replit), что исключает внешний перехват.

Мониторинг: добавлен эндпоинт /api/security-status/, возвращающий состояние настроек безопасности: {"ssl_redirect": true, "hsts_active": true, "secure_cookies": true}.

4. Контейнер в SaaS Replit (Dockerfile v2.0.0)

Исходная виртуальная машина Linux (2000-е годы) более не функционирует, что делает невозможным воспроизведение первоначальной среды сборки. Приложение упаковано в Docker-контейнер на базе python:3.10-slim.

В среде Replit TLS-терминация выполняется автоматически платформенным прокси. Django-приложение работает на порту 3000 и принимает запросы с заголовком X-Forwarded-Proto: https. Middleware HttpsRedirectMiddleware анализирует этот заголовок и при необходимости выполняет редирект 301.

Ключевые параметры контейнера:
  • Базовый образ: python:3.10-slim
  • WSGI-сервер: Gunicorn 21.2 (в контейнере), 2 воркера
  • Порт: 3000
  • HEALTHCHECK: curl -f http://localhost:3000/login/ каждые 30 сек
  • DEBUG=False в контейнере (продакшн-режим)
  • SECURE_SSL_REDIRECT настроен, редирект выполняет HttpsRedirectMiddleware
API мониторинга безопасности:

Эндпоинт GET /api/security-status/ возвращает JSON:

{"ssl_redirect": true, "hsts_active": true, "secure_cookies": true,
 "protocol": "HTTPS", "is_secure": true, "version": "2.0.0"}

5. Тесты по ГОСТ Р 56920 и IEEE 829

Файл тестов: bmc_analyzer/tests.py. Команда запуска: pytest bmc_analyzer/tests.py -v

Спецификация А.В.0001-05-СП — Процедура тестирования:
  1. Открыть терминал в корне проекта.
  2. Выполнить команду: pytest bmc_analyzer/tests.py -v --tb=short
  3. Наблюдать вывод: количество пройденных/упавших тестов.
  4. При наличии упавших тестов зафиксировать: ID теста, ожидаемое и фактическое значения, сообщение об ошибке.
  5. Записать результаты в протокол испытаний.

Критерий завершения: 100% тестов пройдено.

6. Помещение обновлённых продуктов в среду заказчика
Пошаговые инструкции для ИТ-отдела Компании 1:
  1. Подготовка. Создать резервную копию БД: cp db.sqlite3 db.sqlite3.backup_v1
  2. Получение образа. docker pull company2-registry/bmc_analyzer:2.0.0
  3. Остановка предыдущей версии. docker stop bmc_analyzer_v1 && docker rm bmc_analyzer_v1
  4. Запуск новой версии. docker run -d --name bmc_analyzer_v2 -p 3000:3000 -e DJANGO_SECRET_KEY="..." -e REPLIT_DOMAINS="yourdomain.com" -v ./db.sqlite3:/app/db.sqlite3 company2-registry/bmc_analyzer:2.0.0
  5. Применение миграций. docker exec bmc_analyzer_v2 python manage.py migrate
  6. Настройка Nginx — добавить редирект 80→443, SSL-сертификат (Let's Encrypt), заголовок X-Forwarded-Proto https.
  7. Smoke-тест. curl -I http://yourdomain.com/login/ → ожидается 301. curl -I https://yourdomain.com/login/ → ожидается 200 + Strict-Transport-Security.
  8. Проверка API. GET /api/security-status/ → ожидается {"ssl_redirect": true, "hsts_active": true, "secure_cookies": true}
  9. Подтверждение. Уведомить Компанию 2 об успешном вводе в эксплуатацию.
Критерии приёмки:

HSTS активенcurl -I https://...Strict-Transport-Security в ответе
Приложение доступноБраузер → https://Страница входа, иконка замка
Данные сохраненыВход + просмотр таблицВсе команды BMC отображаются

Процедура отката: при критическом дефекте — docker stop bmc_analyzer_v2, восстановить резервную копию БД, запустить v1.
