Задание 1. Стратегия сопровождения для управления модификацией и перемещением программных продуктов (ГОСТ 12207, процесс 6.4)
1.1. Цель и основание

Настоящая стратегия разработана Компанией 2 (разработчик) по запросу Компании 1 (заказчик) и определяет порядок управления модификацией и перемещением программных продуктов BMC_analyzer: веб-приложения и его контейнера. Основанием служит запрос на модификацию MR-2026-001 — переход с незашифрованного протокола HTTP (применявшегося с 2000-х годов) на защищённый протокол HTTPS на всех сайтах Компании 1. Стратегия разработана в соответствии с процессом сопровождения ГОСТ 12207 (§6.4) и стратегией выпусков, основанной на статистических данных вендоров за 2025 год.

1.2. Тип и классификация сопровождения

Выполняемое сопровождение относится к адаптивному типу (Adaptive Maintenance по ГОСТ 12207): изменение среды функционирования (требование безопасного протокола) вынуждает адаптировать программный продукт без изменения его функциональных требований. Параллельно выполняется профилактическое сопровождение (Perfective Maintenance): обновление компонент согласно актуальным версиям вендоров, контейнеризация, добавление заголовков безопасности.

1.3. Стратегия выпусков

Стратегия выпусков определяет состав обновляемых программных компонент на основании статистических данных вендоров за 2025 год (Python Software Foundation, Django Security Releases, Nginx changelog, Let's Encrypt TLS statistics, Docker Hub).

Приоритет: высокий (угроза информационной безопасности — передача данных в открытом виде по протоколу HTTP). Инициатор: руководство Компании 1. Сопровождение выполняется в следующей последовательности шагов:

  1. М-01 (Нед. 1). Анализ запроса на модификацию. Архитектор Компании 2 анализирует запрос MR-2026-001, оценивает объём изменений в приложении и контейнере, фиксирует риски (потеря данных, деградация производительности). Формируется заключение о реализуемости.
  2. М-02 (Нед. 1–2). Разработка технического задания на изменение. Аналитик Компании 2 оформляет ТЗ на изменение: описание модификаций middleware, настроек Django, Dockerfile; перечень затронутых компонент; критерии приёмки.
  3. М-03 (Нед. 2–3). Реализация модификации. Разработчик реализует: HttpsRedirectMiddleware (HTTP→HTTPS 301), SecurityHeadersMiddleware (HSTS, CSP, X-Frame-Options и др.), обновление settings.py, добавление API-эндпоинта /api/security-status/, страницы документации /docs/.
  4. М-04 (Нед. 3). Сборка модифицированного контейнера. DevOps-инженер создаёт Dockerfile на базе python:3.10-slim, собирает образ версии 2.0.0, публикует в реестре образов.
  5. М-05 (Нед. 3–4). Тестирование. QA-инженер выполняет тесты по ГОСТ Р 56920 / IEEE 829: модульные (TC-MOD-01..05), функциональные (TC-FUNC-01..09), приёмочные (TC-ACC-01..02), тесты безопасности HTTPS (TC-HTTPS-01..09), контроля доступа (TC-ACL-01..05), API (TC-API-01..05). Критерий: 100% тестов пройдено.
  6. М-06 (Нед. 4). Передача в среду заказчика. Совместно с ИТ-отделом Компании 1 выполняется развёртывание нового контейнера, обновление конфигурации прокси (Nginx, SSL-сертификат), приёмочный smoke-тест.
  7. М-07 (Нед. 4). Оповещение затронутых сторон. PM Компании 2 направляет Release Notes v2.0.0 всем стейкхолдерам согласно матрице коммуникаций.
Задание 2. Изменения в архитектуре, операциях и интерфейсах существующей системы
2.1. Изменения в архитектуре

До выполнения модификации (версия 1.x) система BMC_analyzer запускалась как Django-приложение, обслуживающее HTTP-запросы напрямую через встроенный сервер разработки (manage.py runserver). Исходный код собирался на виртуальной машине Linux 2000-х годов, которая к моменту выполнения задания уже не функционирует. Шифрование трафика отсутствовало, заголовки безопасности не устанавливались.

После выполнения модификации (версия 2.0.0) архитектура изменена следующим образом. Входящие соединения устанавливаются по протоколу HTTPS с применением TLS 1.3 (RFC 8446). TLS-терминация выполняется на уровне прокси-сервера (Nginx или платформенный прокси Replit). Прокси передаёт запросы к Django-приложению по HTTP на порту 3000, устанавливая заголовок X-Forwarded-Proto: https. При HTTP-запросах (заголовок X-Forwarded-Proto: http) middleware выполняет постоянный редирект 301 на HTTPS-адрес. Приложение упаковано в Docker-контейнер на базе python:3.10-slim, что устраняет зависимость от устаревшей виртуальной машины.

До (v1.x — HTTP, Linux VM)
Браузер → HTTP:80 → Django runserver
— нет шифрования
— нет HSTS, нет CSP
— нет заголовков безопасности

— HttpsRedirectMiddleware (301)
2.2. Изменения в операциях (новые и изменённые программные компоненты)

В ходе модификации созданы и изменены следующие программные компоненты:

  1. bmc_analyzer/middleware.py (создан). Содержит два класса промежуточного ПО: HttpsRedirectMiddleware — перехватывает HTTP-запросы (определяет по заголовку X-Forwarded-Proto: http) и выполняет постоянный редирект 301 на HTTPS-адрес; SecurityHeadersMiddleware — добавляет ко всем ответам заголовки безопасности: Strict-Transport-Security, X-Content-Type-Options, X-Frame-Options, X-XSS-Protection, Referrer-Policy, Permissions-Policy, Content-Security-Policy.
  2. django_project/settings.py (обновлён). Добавлены параметры: SECURE_PROXY_SSL_HEADER, SECURE_HSTS_SECONDS=31536000, SECURE_HSTS_INCLUDE_SUBDOMAINS=True, SECURE_HSTS_PRELOAD=True, SESSION_COOKIE_SECURE, SESSION_COOKIE_HTTPONLY, CSRF_COOKIE_SECURE, CSRF_COOKIE_HTTPONLY. Оба новых middleware добавлены в список MIDDLEWARE первыми позициями. Добавлена конфигурация подсистемы логирования.
  3. bmc_analyzer/views.py (обновлён). Добавлены два новых обработчика: docs(request) — формирует страницу документации по сопровождению; security_status(request) — возвращает JSON-ответ с информацией о текущем протоколе и активных заголовках безопасности.
  4. bmc_analyzer/urls.py (обновлён). Добавлены маршруты: /docs/ и /api/security-status/.
  5. Dockerfile (создан). Контейнер на основе python:3.10-slim с установкой зависимостей, применением миграций, проверкой работоспособности (HEALTHCHECK) и запуском через Gunicorn.
  6. requirements.txt (создан). Зафиксированы зависимости: Django, sympy, pandas, matplotlib, pytest-django, gunicorn.

Задание 4. Разработка модифицированного программного продукта (контейнер) в SaaS Replit
4.1. Обоснование перехода к контейнеризации

Исходные тексты приложения BMC_analyzer собирались на виртуальной машине Linux, созданной в 2000-е годы, которая к моменту выполнения задания более не функционирует. Это исключает возможность воспроизвести первоначальную среду сборки. Для обеспечения воспроизводимости сборки, независимости от конкретного физического или виртуального хоста и упрощения перемещения программного продукта в среду заказчика принято решение упаковать приложение в Docker-контейнер.

4.2. Разработка Dockerfile (контейнер v2.0.0)

Контейнер разработан на базе официального образа python:3.10-slim, выбранного по статистике Docker Hub за 2025 год как наиболее распространённый минималистичный образ для Python-приложений. Dockerfile определяет следующие шаги:

  1. Объявление базового образа python:3.10-slim и метаданных (версия, описание, сопровождающий).
  2. Установка переменных окружения: PYTHONDONTWRITEBYTECODE=1, PYTHONUNBUFFERED=1, DJANGO_SETTINGS_MODULE, DEBUG=False.
  3. Установка минимального набора системных зависимостей (gcc, curl).
  4. Копирование и установка Python-зависимостей из requirements.txt.
  5. Копирование исходного кода приложения.
  6. Сбор статических файлов (collectstatic).
  7. Объявление порта 3000 и команды проверки работоспособности (HEALTHCHECK).
  8. Запуск приложения командой python manage.py runserver 0.0.0.0:3000 (в production-среде — Gunicorn).
FROM python:3.10-slim
LABEL version="2.0.0"
LABEL description="BMC_analyzer — HTTP→HTTPS (MR-2026-001, ГОСТ 12207)"
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1 DEBUG=False
WORKDIR /app
RUN apt-get update && apt-get install -y --no-install-recommends gcc curl \
    && rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
RUN python manage.py collectstatic --noinput 2>/dev/null || true
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=10s CMD curl -f http://localhost:3000/login/ || exit 1
CMD ["python", "manage.py", "runserver", "0.0.0.0:3000"]
4.3. Развёртывание в SaaS Replit

В среде Replit TLS-терминация (HTTPS) выполняется автоматически на уровне платформенного прокси-сервера. Это означает, что к приложению на порту 3000 запросы поступают по HTTP внутри платформы, однако для внешних пользователей соединение защищено HTTPS. Платформа устанавливает заголовок X-Forwarded-Proto: https, который middleware HttpsRedirectMiddleware использует для определения реального протокола клиента. Таким образом, переход на HTTPS обеспечивается комбинацией: платформенный TLS-прокси (транспортный уровень) плюс middleware (уровень приложения).

4.4. Проверка работы API безопасности

После запуска контейнера корректность работы HTTPS-переходa проверяется через эндпоинт GET /api/security-status/ (требует авторизации). Пример ответа: 

{
  "protocol": "HTTPS",
  "is_secure": true,
  "version": "2.0.0",
  "hsts_enabled": true,
  "security_headers": [
    "Strict-Transport-Security", "X-Content-Type-Options",
    "X-Frame-Options", "X-XSS-Protection",
    "Referrer-Policy", "Permissions-Policy", "Content-Security-Policy"
  ]
}
Задание 5. Тесты по ГОСТ Р 56920 (ISO/IEC 29119) и IEEE 829
5.1. Спецификация процедуры тестирования (А.В.0001-05-СП)

Область применения. Настоящая спецификация определяет последовательность действий (процедуры) для выполнения тестов, описанных в спецификации тестов (А.В.0001-05-ТС). Процедуры предназначены для ручного и автоматизированного выполнения в рамках подпроцессов модульного, функционального, приёмочного тестирования и тестирования безопасности (ГОСТ Р 56920, §7.3–7.6).

Процедура автоматизированного тестирования (А.В.0001-05-СП §2).

Цель: проверить корректность функций расчёта индекса угрозы (calculate_risks), генерации графиков, поведение middleware (HTTP→HTTPS, заголовки безопасности), контроль доступа и работу API. Предварительные условия: установлены Python 3.10, Django 5.x, pytest, pytest-django; проект развёрнут в Replit или локально.

  1. Открыть терминал (Shell) в корне проекта.
  2. Выполнить команду: pytest bmc_analyzer/tests.py -v --tb=short
  3. Наблюдать вывод: количество пройденных/упавших тестов.
  4. Если есть упавшие тесты — зафиксировать идентификатор теста, ожидаемое и фактическое значения, сообщение об ошибке.
  5. Записать результаты в протокол испытаний.

Критерий завершения: все тесты выполнены, процент прохождения 100%.

Процедура ручного функционального тестирования (А.В.0001-05-СП §3).

Предварительные условия: сервер запущен (python manage.py runserver), база данных содержит начальные данные (не менее одной команды), учётная запись admin создана, браузер открыт.

Задание 6. Помещение обновлённых продуктов в среду заказчика
6.1. Описание процесса передачи

Передача обновлённых программных продуктов (приложение BMC_analyzer v2.0.0 и контейнер) в производственную среду Компании 1 выполняется в несколько этапов. Процесс организован таким образом, чтобы минимизировать время недоступности системы и обеспечить возможность отката к предыдущей версии.

6.2. Пошаговый план развёртывания
  1. Подготовка. ИТ-отдел Компании 1 получает от Компании 2 следующий пакет: Docker-образ bmc_analyzer:2.0.0 (или доступ к реестру образов), Dockerfile, инструкцию по развёртыванию, SSL-сертификат (или конфигурацию Let's Encrypt). Создаётся резервная копия базы данных SQLite (db.sqlite3) и текущего Docker-образа (если он был).
  2. Получение образа контейнера. На сервере Компании 1 выполняется:
    docker pull company2-registry/bmc_analyzer:2.0.0
  3. Остановка предыдущей версии. Корректная остановка работающего контейнера:
    docker stop bmc_analyzer_v1 && docker rm bmc_analyzer_v1
  4. Запуск новой версии.
    docker run -d --name bmc_analyzer_v2 -p 3000:3000 -e DJANGO_SECRET_KEY="<secret>" -e REPLIT_DOMAINS="yourdomain.com" -v ./db.sqlite3:/app/db.sqlite3 company2-registry/bmc_analyzer:2.0.0
  5. Применение миграций БД (если не выполнено автоматически при старте контейнера):
    docker exec bmc_analyzer_v2 python manage.py migrate
  6. Обновление конфигурации прокси-сервера (Nginx). В конфигурацию добавляется: блок server на порту 80 с редиректом на 443; блок server на порту 443 с директивами ssl_certificate, ssl_protocols TLSv1.3; проксирование запросов на localhost:3000; заголовок proxy_set_header X-Forwarded-Proto https.
  7. Smoke-тест после развёртывания. Последовательно выполнить:
    • curl -I http://yourdomain.com/login/ → ожидается: 301 Moved Permanently, Location: https://yourdomain.com/login/
    • curl -I https://yourdomain.com/login/ → ожидается: 200 OK, заголовок Strict-Transport-Security
    • Вход через браузер: авторизация, просмотр таблиц, проверка иконки замка
    • curl -s -H "Cookie: sessionid=…" https://yourdomain.com/api/security-status/ → ожидается JSON {"protocol":"HTTPS","is_secure":true}
  8. Критерии приёмки. Развёртывание считается успешным при выполнении всех условий: HTTP-запросы перенаправляются на HTTPS (301); HTTPS-страницы доступны и корректно отображаются; заголовок HSTS присутствует в ответах; данные в БД не потеряны; все пользователи могут выполнить вход в систему.
  9. Процедура отката. В случае обнаружения критического дефекта в течение 24 часов после развёртывания: остановить bmc_analyzer_v2, восстановить резервную копию БД, запустить bmc_analyzer_v1, уведомить Компанию 2.
